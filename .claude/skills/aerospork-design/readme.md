# AeroSpork Design System

AeroSpork is an i3-like tiling window manager for macOS: tree layout, virtual workspaces, TOML
configuration, a CLI, and a settings GUI. It is a fork of
AeroSpace (MIT). The repository README covers what the
product is and how it differs from upstream. This document covers how it looks and how it is worded.

## Sources this system was built from

| Source | What was read |
|---|---|

| AeroSpace | Named as upstream for context only. Nothing was copied from it. |

No Figma file, no design file, and no written brand guidelines exist for this product. **Everything
here is derived from the Swift source and the docs.** If you have access to the repo, read
`Sources/AppBundle/ui/` before you design anything new: the comments in those files are the closest
thing AeroSpork has to a design rationale document, and they explain *why* each control looks the way
it does.

There is **no logo or wordmark** in the repo. The only brand artwork is the app icon. Its source is
`assets/icon/render.html` in this skill, and the shipping icon files are rendered from it.
Wherever a wordmark is needed, "AeroSpork" is set in the system font, semibold, with
tight tracking (see `thumbnail.html`, `assets/icon/Banner.html`).

## Products / surfaces

1. **AeroSpork.app — Settings GUI** (`Sources/AppBundle/ui/`, SwiftUI/AppKit). Seven peer panes in a
   native macOS preferences toolbar: General, Gaps, Keys, Monitors, Events, Window Rules, Raw TOML.
   880×620 ideal, 780×520 minimum. Structured panes
   apply live on a 600 ms debounce. There is no Save button.
2. **AeroSpork.app — menu bar extra** (`MenuBar.swift`, `MenuBarLabel.swift`). A monochrome chip per
   visible workspace, and a short menu that is a *remote control*, not a control panel.
3. **`aerospork` CLI.** Commands, man pages and shell completion: a thin client over a Unix socket.
   Silent on success, one line on failure.
4. **Docs site.** Asciidoctor's default output from `docs/*.adoc`, served under `/docs/` on the
   hosted site. It has no custom design. On the hosted site, `docs/index.html` redirects to
   `/docs/guide.html`. Only a local `.site` build keeps the redirect to GitHub. Nothing in this
   system styles it.

## Content fundamentals

The voice is a careful engineer explaining a decision to another engineer. Match it before you
match the pixels.

**Person and address.** Second person for the user ("your config", "you would rather click"),
never "we". The app never refers to itself in the first person. Feature docs describe what the
software does, in plain present tense: "Runs once, after AeroSpork finishes launching."

**Casing.** Sentence case everywhere — labels, buttons, section headers, pane labels.
`Start AeroSpork at login`, not `Start AeroSpork At Login`. Pane labels are one word where possible
(General, Gaps, Keys, Monitors, Events). The one exception is *Window Rules*. Product name is always
`AeroSpork`. The binary, the config keys and the CLI are always lowercase `aerospork`.

**Explain the consequence, not the control.** Help text says what happens, and why you would care:

> "The top gap is measured below the menu bar, so 0 is flush with the usable area."
> "Auto gives wide monitors a horizontal split and tall monitors a vertical one."
> "Both icons off would leave no way into Settings, so the Dock icon is kept."

**Name the state, then the recovery.** Error copy never stops at the diagnosis:

> "Your config was not loaded — AeroSpork is running built-in defaults. Fix the errors below and
> save; the config reloads by itself."

**Say what is not written in the file.** A recurring theme: the GUI is honest about the layers under
it. "12 generated by mod, 4 written in your config. Generated bindings have no line to edit —
Override copies one here first."

**Empty states teach the feature**, they do not announce emptiness: "Rules run once, when a window
first appears: the usual use is sending an app straight to its workspace."

**Punctuation and typography.** Prefer a colon before an explanation, a comma around a short aside,
and a full stop between two independent clauses. Keep the em dash for the rare interruption none of
those handle. More than one per screen of prose means the sentences want splitting. `…` on menu items
that open something (`Settings…`, `Restore…`, `New Mode…`). Curly quotes around user-supplied names:
`Leave “service” mode`. Keyboard shortcuts as glyphs (`⌘,`, `⌥⇧h`), never as words. Numbers are
plain. Units are a separate secondary label (`8` `pt`).

**No exclamation marks, no emoji, no jokes, no marketing adjectives.** Emoji appear in exactly one
place in the codebase, as a *problem being handled*: a workspace named with an emoji is drawn bare in
the menu bar because scaling it into a chip turns it into a smudge. Never add emoji to a surface.

**Placeholders are real examples**: `com.apple.finder`, `focus left`, `move-node-to-workspace 3`,
`mode name, e.g. resize`, never "Enter a value".

**Tooltips double as accessibility labels**, so they are written as names: an icon-only + button's
help is "Pin a workspace to a monitor", not "Click to add".

## Visual foundations

**The look is native macOS, unstyled.** AeroSpork paints in system semantic colors and the system
font, and then gets out of the way. There is no custom control skin, no brand color on a button, no
gradient anywhere in the UI. The only place the brand has its own palette is the app icon. When you
design a new AeroSpork surface, match AppKit's defaults.

**Color.** Six system colors (blue, red, orange, green, yellow, gray) with light and dark values, plus
label hierarchy defined as opacity on black (85% / 50% / 26% / placeholder 25%), never as gray hexes.
Accent is `controlAccentColor`, that is, system blue by default. Let a user's chosen accent
override it. Color carries meaning only: red = config not loaded, orange = warning, green = valid.
Brand palette: plate `#1C202C → #10121A`, focused pane `#5E9EFF`, dimmed pane `#4E566A`.

**Type.** San Francisco through the system font, at the sizes macOS resolves its text styles to:
13px body, 12px hints/footers, 11px pane labels and table headers, 13px semibold section headers,
10px badges. Monospaced (SF Mono) for *anything the user could type into the config file*: commands,
key notation, app ids, paths, UUIDs, versions, format strings. SF Rounded semibold appears in exactly
one place: the menu bar workspace chips.

**Spacing.** AppKit metrics, odd numbers included: 5, 6, 7, 9, 11, 14. `.padding(.vertical, 9)` on a
bar strip, `7px` above a +/- row, `16px` at a Form's edge. Do not round these to a 4/8 grid. The
source says 9, so it is 9.

**Corner radii.** 4 tile · 5 recorder · 8 field, button and row · 8 for the schematic panels that
the Swift draws itself (the gaps preview and the monitor arrangement) · 10 card (`--radius-card`, an
approximation of the grouped Form section that AppKit draws) · 14 window · capsule for badges and
the mode chip. Every rounded rect in the app is `style: .continuous` (a squircle). CSS
`border-radius` is an approximation, so at large sizes (the icon) use the real squircle geometry:
22.5% corner ratio on artwork inset 5.5% from the canvas.

**Backgrounds.** Flat fills only, no images, no patterns, no textures, no gradients in the UI. A
grouped Form is white boxes on `--grouped-bg`. Chrome strips are translucent `.bar` material with a
blur. Schematic shapes use `Color.primary.opacity(0.045 / 0.06 / 0.08)`. The only imagery in the
brand is product screenshots (`assets/product/`), which are literal captures of tiled windows —
cool, neutral, no filters or grain. Marketing surfaces (README banner, App Store hero) are the one
place a dark plate gradient and a soft blue glow are allowed, because they are extensions of the icon.

**Borders and shadows.** Hairline `1px` separators at 10% black / 15% white do most of the work.
Controls get a 0.5px border plus a `0 0.5px 1.5px rgba(0,0,0,.14)` lift — nothing bigger. Cards have
no drop shadow at all. They are a fill plus a hairline. Real shadows exist only on things that float:
menus, popovers, and a window in a screenshot. No inner shadows except the 1px inset on a text field.

**Transparency and blur** are for chrome that overlaps content — toolbars, path bars, action bars,
menus, and nothing else. Content surfaces are opaque.

**Animation.** Essentially none, on purpose: the product's whole claim is that workspace switching is
*instant*, because workspaces are emulated rather than handed to macOS Spaces. Never animate a
workspace switch, a pane change or a layout change. What remains is standard AppKit control feedback
(~120 ms), menu/popover appearance (~180 ms), and one product timing worth knowing: the CopyButton
checkmark holds for 1.4 s. Layout refreshes are debounced at 50 ms. Settings apply live 600 ms
after the last change.

**Hover, press, focus, disabled.** Hover is a faint fill (4.5–6% ink) on rows and menu items, never a
color change or a shadow. Press darkens the fill slightly. Nothing scales or bounces. Focus is the
system focus ring, plus one custom state worth copying: an *armed* key recorder fills accent at 14%
and draws a 2px accent border. Disabled is 40% opacity of the whole control, and a disabled button
still occupies its space — Remove stays visible when nothing is selected.

**Selection** in a table is a full-width `selectedContentBackgroundColor` bar with white text.

**Layout rules.** One toolbar strip at the top and one action strip at the bottom, both pinned, with
the scrolling content between them. Never stack two bar strips — merge their contents. Tables live
edge-to-edge. Forms get 16px padding. Fixed control widths (58px number field, 150px recorder,
170px composer recorder) are copied verbatim. A pane that can be empty always has an empty state.

**Cards** are `--control-bg` fill, `--radius-card` (10px) corners, a 0.5px hairline, and no shadow.

## Iconography

**The app's real icon set is SF Symbols**, at the Regular weight, used at 12–17px inline and 34px
Light for empty-state glyphs. Every glyph in the shipped UI is a system symbol referenced by name
(`gearshape`, `display.2`, `arrow.triangle.branch`, `exclamationmark.octagon.fill`). There is no
custom icon font, no SVG sprite, and no PNG icon in the repo apart from the app icon and the
documentation screenshots.

**Substitution (flagged).** SF Symbols cannot be redistributed in a web design system, so
`components/icons/Icon.jsx` maps the ~40 symbol names the app actually uses onto the closest
[Lucide](https://lucide.dev) icons (ISC) and inlines their geometry as `currentColor` SVG, no CDN,
so mocks render offline. The same shapes are on disk in `assets/icons/`. Pass the *SF Symbol* name
(`<Icon sf="gearshape" />`) so a mock stays traceable to the Swift source. Shapes are
close, not identical — `display.2` and `rectangle.inset.filled` are the loosest matches. **In
production Swift, always use the SF Symbol name.**

Rules that hold in both worlds: icons are monochrome and inherit the text color. They are tinted
only to carry a status (red/orange/green). An icon never appears without either a label or a
tooltip that reads as its name. **Emoji are never used as icons**. Unicode glyphs *are* used, for
one thing only: modifier keys (`⌃⌥⇧⌘`) and the shortcut hints in menus.

Available assets: `assets/icon/` (new layered icon set, banner, App Store hero),
`assets/icon-legacy/` (the icon this one replaced), `assets/product/` (tiling screenshots and the
repo's monitor-arrangement diagrams).

## App icon

The mark is the layout: one focused pane on the left, three stacked panes on the right. It comes
from the repo's original `generate-app-icon.py`, since removed, along with the two constraints that
shaped it.
`assets/icon/README.md` documents those, the layer breakdown, and how to rebuild the set.

This system adds an **Icon Composer-style layered version** of that same mark: plate gradient →
top-light layer → rim bevel → glass panes with specular highlights, in three variants (default dark
plate, light plate, monochrome/tinted). This layered version is the one that ships. See
`assets/icon/README.md` for the layer breakdown and how to rebuild the set.

### Components

Grouped by concern. Every one of these has a counterpart in `Sources/AppBundle/ui/`. Nothing was
invented to round out a "standard" set.

**`components/controls/`.** `Button`, `Toggle`, `TextField`, `NumberField`, `SegmentedPicker`,
`Select`, `CopyButton`, `IconButton`, `KeyRecorderField`, `KeyCaps`

**`components/layout/`.** `FormSection`, `SectionLabel`, `SettingsHint`, `SettingsFooter`,
`BarStrip`, `ListActionBar`, `PanelHeader`, `TabBar`, `LabeledContent`, `DataTable`, `MenuPanel`

**`components/feedback/`.** `Banner`, `StatusLabel`, `ContentUnavailable`, `Badge`

**`components/brand/`.** `AppIcon`, `WorkspaceChips`, `GapsPreview`, `MonitorArrangement`,
`CodeEditor`, `WindowChrome`

**`components/icons/`.** `Icon`

#### Intentional additions

- **`Icon`.** a wrapper, not a new UI idea. The app uses SF Symbols directly and a web system needs
  a glyph component.
- **`BarStrip`**, **`LabeledContent`**, **`DataTable`**, **`MenuPanel`**, **`TabBar`**,
  **`WindowChrome`.** these are SwiftUI/AppKit constructs the app uses pervasively
  (`.background(.bar)`, `LabeledContent`, `Table(...).tableStyle(.inset)`, `MenuBarExtra`, `TabView`,
  the window itself) rather than components defined in `SettingsChrome.swift`. They are here because
  a web recreation has to draw them by hand.

Not built, because the source has no such thing: toasts, avatars, breadcrumbs, modals, cards with
imagery, charts. AeroSpork has no notification surface at all — persistent banners and inline status
labels are the only feedback surfaces.

## Caveats

- **Fonts:** none are shipped, and none should be. The app uses the system font. `--font-system`,
  `--font-mono` and `--font-rounded` resolve to San Francisco / SF Mono / SF Rounded on macOS and
  fall back to the platform UI font elsewhere. Non-Apple platforms will not match the real product.
- **Icons are a Lucide substitution** for SF Symbols (see Iconography).
- **CLI output strings** in `ui_kits/cli/` are illustrative sample data in real output *shapes*.
- The dark appearance is applied with `[data-appearance="dark"]`, not `prefers-color-scheme`, so a
  mock can show both side by side.
